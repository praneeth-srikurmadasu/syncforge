# ADR-0020: Angular frontend with signals and server state, no store library, generated API types

- **Status:** Accepted
- **Date:** 2026-11-12

## Context
Phase 8 adds an administration application on top of the existing API: 51 operations
over employees, connectors, workflows, events, dead letters, conflicts, audit and
membership. The backend is the authority for every rule, including permissions,
conflict policy, workflow validity and retries. Most of what the UI shows is server data
that changes in the background (worker, relay).

## Problem
How to structure the frontend so that it stays faithful to the API contract, shows only
real data, handles the API's errors explicitly, and remains small enough for one
engineer to explain and maintain.

## Considered alternatives
| Option | Assessment |
|---|---|
| NgRx store with effects for all data | Adds a second copy of server state, plus actions, reducers and selectors for each of about 25 screens; little benefit when nearly all state is "the last API response for this screen". |
| A UI component library (Angular Material or similar) | Fast start, but its look and density fight a data-heavy admin design, and it adds weight; about 20 small components on CSS tokens cover what is needed. |
| Hand-written TypeScript interfaces for API payloads | Drift silently from the backend. |
| **Standalone components, signals, `httpResource` per screen, URL as filter state, types generated from OpenAPI** | Matches Angular 22's direction, little code, and the compiler catches contract changes. |

## Decision
- Standalone components with `OnPush` and zoneless change detection; one lazy route per page.
- Reads through `httpResource` (loading / error / value signals; superseded requests are
  cancelled when filters change). Writes through typed API services returning observables,
  followed by a resource reload. No store library.
- Filters, sort and paging live in the URL query string.
- API types are generated by `openapi-typescript` from a committed OpenAPI snapshot;
  `npm run api:check` fails when they drift.
- One `ApiError` type built in an interceptor; errors are never swallowed.
- The permission matrix is mirrored only to decide what to show; the API enforces it.
- The bearer token is held in memory and mirrored to `sessionStorage`, so a reload keeps
  the session in that tab. This is not XSS protection; it is documented as such.
- Background progress is followed by polling, because the API has no push channel.

## Trade-offs
- Polling costs requests; screens poll only while switched on and the tab is visible.
- Without aggregate endpoints the dashboard makes about 40 `limit=1` requests.
- `sessionStorage` exposes the token to any script in the page, as memory would; an
  HttpOnly-cookie session would need backend changes.
- An own design system is more code to own than a library, but it is small and tested
  by the axe checks in the browser suite.

## Consequences
- Contract changes surface as compile errors (`api:types`) rather than runtime bugs.
- Screens are independent: one page's failure does not affect another, and dashboard
  figures fail one by one.
